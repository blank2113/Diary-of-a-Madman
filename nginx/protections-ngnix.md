# 🛡️ **Защита от DDoS, таймауты и буферы в Nginx**

Nginx часто выступает в роли первого рубежа обороны (Edge-сервера) перед вашим приложением на NestJS/Node.js. За счет своей асинхронной архитектуры он способен выдерживать огромный наплыв «мусорного» трафика, отсекая вредоносные или неоптимальные запросы до того, как они доберутся до тяжелого бэкенда и положат базу данных.

Ниже описаны конфигурации для защиты от низкоуровневых и прикладных (L7) атак, а также правила тонкой настройки буферов и таймаутов под высокую нагрузку.

---

## 1. Защита от L7 DDoS-атак и парсеров (Rate Limiting)

Атаки на прикладном уровне (HTTP) часто пытаются симулировать поведение реальных пользователей, но с огромной частотой (например, спам эндпоинта `/api/v1/auth/login` с целью подбора паролей или вызова тяжелых криптографических функций хэширования).

Nginx позволяет жестко ограничить количество запросов с одного IP-адреса с помощью алгоритма **Leaky Bucket (Протекающее ведро)**.



### Конфигурация лимитов запросов и соединений:
```nginx
http {
    # 1. Ограничение частоты запросов (Rate Limiting)
    # $binary_remote_addr — индексируем клиентов по их бинарному IP (всего 4 байта на адрес для экономии памяти)
    # zone=api_limit:10m — выделяем 10 МБ оперативной памяти под хранение истории IP-адресов (хватит на ~160 000 адресов)
    # rate=5r/s — разрешаем этому IP делать не более 5 запросов в секунду
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s;

    # 2. Ограничение одновременных TCP-соединений (Connection Limiting)
    # Запрещает одному IP-адресу открывать слишком много сокетов одновременно (защита от DDOS-софта)
    limit_conn_zone $binary_remote_addr zone=connections_limit:10m;

    server {
        listen 443 ssl http2;
        server_name api.mysite.com;

        # Применяем ограничение соединений на весь сервер (максимум 20 одновременных сокетов от одного IP)
        limit_conn connections_limit 20;

        location /api/v1/auth/ {
            # Применяем лимит частоты запросов
            # burst=10 — «буфер сглаживания». Если пользователь случайно за секунду сделал 7 запросов, 
            # первые 5 обработаются сразу, а 2 повиснут в очереди, а не упадут с ошибкой.
            # nodelay — указывает Nginx, что запросы из буфера burst нужно обрабатывать сразу, 
            # не размазывая их искусственно по времени, но строго соблюдая лимит емкости "ведра".
            limit_req zone=api_limit burst=10 nodelay;

            proxy_pass http://nestjs_backend;
        }
    }
}
```
>Что увидит атакующий? Если лимит превышен, Nginx мгновенно вернет клиенту статус 503 Service Temporarily Unavailable, даже не отправляя запрос в Node.js.


## 2. Защита от атаки Slowloris (Таймауты)

Атака Slowloris гениальна в своей простоте: атакующий открывает сотни TCP-соединений с Nginx и начинает отправлять HTTP-заголовки невероятно медленно (например, по одному байту в 10 секунд). Из-за этого потоки или сокеты сервера остаются заняты ожиданием окончания запроса, и у сервера заканчиваются свободные лимиты для реальных пользователей.

Чтобы защититься от этого, нужно принудительно заставить Nginx закрывать сокеты, если клиент «молчит» или шлет данные слишком вяло.

Тюнинг сетевых таймаутов (Блок server или http):

```nginx
# Время, в течение которого Nginx ждет от клиента чтения заголовка запроса. 
# Если клиент не уложился в 10 секунд, соединение рвется.
client_header_timeout 10s;

# Время, в течение которого Nginx ждет тело запроса (например, загрузку JSON или картинки).
client_body_timeout   10s;

# Таймаут для Keep-Alive соединений. Сколько времени держать сокет открытым 
# после ответа, ожидая от браузера следующий запрос. 65 секунд — стандарт для веба.
keepalive_timeout     65s;

# Время, в течение которого клиент обязан принять ответ от Nginx. 
# Если пользователь «повис» и не читает байты 10 секунд — закрываем сокет.
send_timeout          10s;
```


## 3. Защита от переполнения памяти: Настройка буферов

Если клиент отправляет на сервер огромный заголовок (например, со спамом из фальшивых Cookie-файлов) или пытается загрузить гигантский JSON, Nginx начинает выделять под этот запрос оперативную память. Если буферы не настроены, Nginx начнет сбрасывать эти данные во временные файлы на жесткий диск, что резко снизит скорость работы (вызовет дисковый I/O-bottleneck).

Оптимизация размеров буферов:

```nginx
# Ограничиваем максимальный размер тела запроса (защита от загрузки файлов по 100ГБ, которые забьют диск)
client_max_body_size 5m; # Разрешаем загружать файлы/JSON максимум до 5 Мегабайт

# Размер буфера в оперативной памяти для чтения тела запроса клиента
client_body_buffer_size 128k;

# Размер буфера для чтения заголовков запроса клиента (обычно 1кб-4кб хватает с головой, ставим 4кб)
client_header_buffer_size 4k;

# Максимальное количество и размер буферов для больших заголовков (если у пользователя огромные JWT в куках)
large_client_header_buffers 4 16k;
```


## 4. Сброс некорректных запросов: Оптимизация на уровне ядра
Если к вам прилетает запрос с некорректным или фальшивым именем хоста (например, атакующие сканируют ваш IP-адрес напрямую, минуя доменное имя), не нужно отдавать им дефолтную страницу. Лучше сразу оборвать TCP-соединение на уровне сокета без отправки HTTP-ответа.

Для этого в Nginx есть встроенный недокументированный код ответа 444 Connection Closed Without Response.

```nginx
# Дефолтный сервер, который принимает на себя весь неопознанный трафик (по IP или чужим доменам)
server {
    listen 80 default_server;
    listen 443 ssl http2 default_server;
    server_name _;

    # Заглушка для SSL, чтобы Nginx не ругался (можно сгенерировать самоподписанный)
    ssl_certificate /etc/nginx/ssl/dummy.crt;
    ssl_certificate_key /etc/nginx/ssl/dummy.key;

    # Мгновенно рвем TCP-соединение на уровне ядра Linux. 
    # Сканнеры и боты не получают вообще ничего в ответ (жадный сброс)
    return 444; 
}
```

## Резюме оборонной стратегии:
  * Rate-limiting (limit_req) защищает ваше Node.js/NestJS приложение от перегрузки по CPU.

  * Таймауты (client_header_timeout) защищают сам Nginx от исчерпания свободных сокетов при медленных атаках (Slowloris).

  * Лимиты размеров (client_max_body_size) гарантируют, что жесткий диск сервера не будет забит мусорными логами или тяжелыми бинарными файлами.

  * Код ошибки 444 экономит ваш исходящий сетевой трафик, полностью игнорируя автоматизированные сканеры уязвимостей.
