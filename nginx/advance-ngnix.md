# 🚀 **Продвинутый Nginx: Оптимизация, Микросервисы и Подкапотная Магия**

Когда инфраструктура проекта перерастает базовый уровень, Nginx перестает быть просто утилитой для раздачи HTML. В высоконагруженных продакшен-системах он берет на себя роль **API Gateway**, **Edge-сервера**, интеллектуального кэшера и первого рубежа сетевой безопасности.

Ниже подробно разобраны продвинутые концепции, архитектурные хаки и конфигурации, которые используются инженерами для выжимания максимальной скорости и стабильности.

---

## 1. Микросервисный роутинг и API Gateway (Разделение стримов)

В современной микросервисной архитектуре вместо одной монолитной системы бэкенд состоит из десятков изолированных сервисов (сервис авторизации, сервис заказов, сервис аналитики). Клиент (браузер или мобильное приложение) не должен знать IP-адрес каждого микросервиса. 

Nginx выступает в роли **API Gateway** — единой точки входа, которая анализирует URL запроса и бесшовно перенаправляет трафик в нужный закрытый сегмент сети.



### Практическая конфигурация роутинга:
```nginx
# Пул нод для микросервиса авторизации (работает быстро, критичен к аптайму)
upstream auth_service {
    server 10.0.1.10:3001;
    server 10.0.1.11:3001;
}

# Пул нод для микросервиса обработки заказов (тяжелые транзакции)
upstream orders_service {
    server 10.0.2.50:3002;
    server 10.0.2.51:3002;
}

server {
    listen 443 ssl http2;
    server_name api.production.com;

    # Глобальное ограничение на размер загружаемых файлов (например, картинок/документов)
    client_max_body_size 10m;
    
    # -----------------------------------------------------------------
    # 1. Маршрут к микросервису авторизации
    # -----------------------------------------------------------------
    location /api/v1/auth/ {
        proxy_pass http://auth_service;
        
        # Высокоэффективная директива: если одна нода упала (502) или таймаутит, 
        # Nginx мгновенно перебросит этот же запрос клиента на вторую живую ноду.
        proxy_next_upstream error timeout http_502; 
        
        # Жесткие тайм-ауты: авторизация не должна заставлять пользователя ждать
        proxy_connect_timeout 2s;
        proxy_read_timeout 5s;
    }

    # -----------------------------------------------------------------
    # 2. Маршрут к микросервису заказов
    # -----------------------------------------------------------------
    location /api/v1/orders/ {
        proxy_pass http://orders_service;
        
        # Даем бэкенду больше времени на обработку (например, на связь с платежным шлюзом)
        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
    }

    # Безопасность: Запрещаем доступ к скрытым системным файлам (.git, .env)
    location ~ /\. {
        deny all;
        access_log off;
        log_not_found off;
    }
}
```

## 2. Прокси-кэширование динамических данных (Proxy Cache)
База данных и бэкенд на Node.js/NestJS тратят огромное количество ресурсов CPU и памяти на обработку одинаковых тяжелых запросов (например, каталог товаров на главной странице, который обновляется раз в 15 минут).

Nginx умеет сохранять JSON-ответы бэкенда на свой локальный диск/память и отдавать их последующим пользователям со скоростью отдачи статики, вообще не беспокоя Node.js.

Конфигурация Proxy Cache:

```nginx
# Описываем зону кэша в блоке http (вне блока server)
# /var/cache/nginx — путь к файлам кэша на диске
# levels=1:2 — иерархия папок (чтобы Linux не тормозил при миллионах файлов в одной директории)
# keys_zone=api_cache:10m — выделяем 10 МБ оперативной памяти под хранение «ключей» (индекса) кэша
# max_size=1g — максимальный объем кэша на диске. При превышении старый кэш удаляется
# inactive=60m — если к файлу кэша не обращались 60 минут, он стирается
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api_cache:10m max_size=1g inactive=60m;

server {
    listen 443 ssl http2;
    server_name api.production.com;

    location /api/v1/catalog/top {
        proxy_pass http://nestjs_backend;
        
        # Активируем созданную зону кэша
        proxy_cache api_cache;
        
        # Уникальный ключ кэширования: схема + метод + хост + точный URL с query-параметрами
        proxy_cache_key "$scheme$request_method$host$request_uri";

        # Указываем, какие ответы кэшировать и на сколько
        proxy_cache_valid 200 10m;  # Успешные ответы кэшируем на 10 минут
        proxy_cache_valid 404 1m;   # Ошибки "Не найдено" кэшируем на 1 минуту, чтобы снизить спам-нагрузку

        # Спасительные директивы (Анти-Авария):
        # Если бэкенд упал (error/timeout/502), Nginx продолжит отдавать пользователям 
        # старый (устаревший) кэш из своей памяти, пока система не восстановится!
        proxy_cache_use_stale error timeout updating http_500 http_502;
        
        # Защита от "Наплыва" (Thundering Herd): только один (первый) запрос уйдет на бэкенд 
        # генерировать кэш, остальные будут ждать его в очереди Nginx, снижая пиковую нагрузку
        proxy_cache_lock on;

        # Пробрасываем в заголовок ответа статус кэша (HIT — отдал Nginx, MISS — запрос ушел на Node.js)
        # Очень удобно для отладки в DevTools
        add_header X-Cache-Status $upstream_cache_status;
    }
}
```

## 3. A/B Тестирование и Канареечные релизы (split_clients)
Выкатывать новую версию API или фронтенда сразу на 100% пользователей — огромный риск. Продвинутый подход подразумевает использование встроенного модуля split_clients. Он хэширует строку (например, IP-адрес клиента) и на основе этого распределяет пользователей по группам в процентном соотношении.

Конфигурация распределения трафика:

```nginx
# Настройка в блоке http
# Хэшируем бинарный IP-адрес клиента и распределяем переменную $backend_pool
split_clients "${binary_remote_addr}" $backend_pool {
    10%     nestjs_v2_new_features; # 10% аудитории увидят новые фичи
    * nestjs_v1_stable;       # Все остальные 90% сидят на стабильной версии
}

upstream nestjs_v1_stable { server 10.0.5.1:3000; }
upstream nestjs_v2_new_features { server 10.0.5.2:3000; }

server {
    listen 443 ssl http2;
    server_name application.com;

    location / {
        # Маршрутизируем запрос на апстрим, имя которого динамически вычислено модулем split_clients
        proxy_pass http://$backend_pool;
        
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

## 4. Оптимизация соединений бэкенда: Keep-Alive Upstream
По умолчанию Nginx общается с пользователем по длинному соединению (HTTP/1.1 или HTTP/2), но при пересылке запроса на внутренний Node.js/NestJS сервер он использует протокол HTTP/1.0. Это означает, что на каждый чих клиента Nginx заново открывает и закрывает локальный TCP-сокет до Node.js.

При высокой нагрузке операционная система сервера забивается сокетами в состоянии TIME_WAIT, что приводит к нехватке свободных портов и замедлению работы.

Конфигурация постоянных сокетов до бэкенда:

```nginx
upstream nestjs_cluster {
    server 127.0.0.1:3000;
    
    # Ключевой параметр: держать открытыми до 32 постоянных TCP-соединений к бэкенду
    keepalive 32; 
}

server {
    listen 80;
    
    location / {
        proxy_pass http://nestjs_cluster;
        
        # Обязательные директивы для активации keepalive внутри пула!
        proxy_http_version 1.1;       # Явно переключаем прокси на HTTP/1.1
        proxy_set_header Connection ""; # Очищаем заголовок "Close", разрешая удерживать сокет
    }
}
```

## 5. Подкапотная магия: Как на самом деле работает try_files?
Директива try_files $uri $uri/ /index.html; — фундамент для работы SPA-приложений (React, Vue). Мало кто понимает, что именно делает Nginx на диске сервера при её выполнении.

Когда приходит запрос на путь mysite.com/profile:

  * $uri: Nginx проверяет, есть ли на диске в корневой папке конкретный файл с именем profile. (Не нашел).

  * $uri/: Nginx проверяет, есть ли на диске папка profile/ и есть ли в ней индексный файл (index.html). (Не нашел).

  * /index.html: Так как первые два шага провалились, Nginx выполняет внутренний редирект (Internal Redirect). Он сбрасывает текущее состояние и заново запускает цикл обработки запроса, принудительно отдавая файл /index.html.

Браузер получает этот HTML-файл, инициализирует JavaScript-код вашего React-приложения, и встроенный клиентский роутер (React Router) уже на стороне клиента парсит URL и отрисовывает страницу /profile.


## 6. Автоматизация SSL в горячем режиме: Let's Encrypt Webroot
Популярный метод генерации SSL-сертификатов через Certbot в режиме --standalone требует временной остановки веб-сервера, так как утилита пытается сама занять 80-й порт. В продакшене останавливать Nginx даже на 3 секунды нельзя.

Решение — использование режима Webroot. Certbot просто подкладывает временный секретный файл в указанную папку, а рабочий Nginx его мгновенно отдает проверяющему роботу Let's Encrypt.

```nginx
server {
    listen 80;
    server_name mysite.com;

    # Специальный эндпоинт, куда постучится бот Let's Encrypt для проверки домена
    location /.well-known/acme-challenge/ {
        root /var/www/letsencrypt_validation;
    }

    # Всех остальных пользователей безопасно перенаправляем на HTTPS
    location / {
        return 301 https://$host$request_uri;
    }
}
```

Команда генерации/обновления без простоя:

```sudo
sudo certbot certonly --webroot -w /var/www/letsencrypt_validation -d mysite.com -d [www.mysite.com](https://www.mysite.com)
```

## 7. Логика на JS прямо внутри веб-сервера: Модуль njs

Если стандартных условий конфигурационного файла Nginx начинает не хватать (а директива if в Nginx работает специфично и её использование не рекомендуется в блоках location), можно использовать njs (Nginx JavaScript).

Это легковесный встроенный движок JavaScript, разработанный создателями Nginx. Он позволяет писать JS-код, который выполняется внутри этапов обработки запроса с минимальными задержками.

### Шаг 1: Пишем JS-скрипт (/etc/nginx/auth.js)

```javascript
function verifyToken(r) {
    // Читаем кастомный заголовок запроса
    var secretToken = r.headersIn['X-Secret-Token'];
    
    if (secretToken === 'super-secure-production-key') {
        r.return(200, "Авторизация пройдена успешно на уровне Nginx!");
    } else {
        r.return(403, "Ошибка авторизации: неверный токен Edge-уровня.");
    }
}

export default { verifyToken };
```

### Шаг 2: Подключаем его в nginx.conf
```nginx
# Загружаем модуль
js_import /etc/nginx/auth.js;

server {
    listen 80;
    server_name api.mysite.com;

    location /secure-gateway {
        # Передаем управление обработкой контента нашей JS функции
        js_content auth.verifyToken; 
    }
}
```
> Это позволяет реализовывать кастомное логирование в JSON, динамический роутинг на основе сложных Cookie-файлов или фильтрацию спам-запросов, разгружая ресурсы основного Node.js приложения.

## Чек-лист Senior-конфигурации:

  * Использовать proxy_next_upstream для защиты от падения одиночных бэкенд-нод.

  * Всегда настраивать keepalive в блоках upstream для повторного использования TCP-соединений.

  * Включать proxy_cache_use_stale, чтобы Nginx спасал пользователей заглушками с кэшем при авариях бэкенда.

  * Проверять синтаксис конфига командой nginx -t перед каждым применением изменений на сервере.
