# 🚀 Что такое мультиплексирование и как оно устроено?

Чтобы понять, какой прорыв совершил HTTP/2, нужно вспомнить главную боль **HTTP/1.1**. В старой версии протокол был текстовым. Запрос и ответ летели в виде сплошного куска текста. Из-за этого внутри одного TCP-соединения нельзя было перемешать данные: пока сервер не закончит передачу текста огромной картинки, он физически не может начать отправку маленького JSON-ответа. Браузеру приходилось открывать до 6 параллельных TCP-сокетов (пулинг), но даже это не спасало, если ресурсов на странице было много.

**HTTP/2 полностью изменил правила игры, внедрив мультиплексирование.** Мультиплексирование — это технология, которая позволяет параллельно отправлять и принимать множество независимых запросов и ответов внутри **одного-единственного TCP-соединения**. Больше никаких 6 сокетов — бэкенд и браузер общаются через один общий «провод».

---

### 🧩 Три кита HTTP/2: Фреймы, Стримы и Соединение

Чтобы перемешивать данные без каши, HTTP/2 ввел строгую иерархию абстракций. Передача данных больше не является хаотичным текстовым потоком. Она разбита на три уровня:

1.  **Фрейм (Frame) — неделимый кирпичик данных.** HTTP/2 отказался от ASCII-текста в пользу бинарного формата. Теперь всё разбивается на мелкие бинарные пакеты — фреймы. У каждого фрейма есть длина, тип и строгий заголовок.
    * `HEADERS Frame` — содержит только сжатые заголовки запроса или ответа.
    * `DATA Frame` — содержит кусок сырого тела (например, часть JSON-строки или кусок байт картинки).
    * `SETTINGS Frame` — служебный фрейм, которым сервер и клиент согласовывают лимиты.
2.  **Стрим (Stream) — логический канал (нить).**
    Стрим — это виртуальный двунаправленный поток фреймов в рамках одного запроса-ответа. Например, когда клиент запрашивает файл `avatar.png`, под этот запрос выделяется, допустим, `Stream ID: 3`. Все фреймы заголовков и данных, относящиеся к этой аватарке, будут помечены тройкой.
3.  **Соединение (Connection).**
    Это физический TCP-сокет, внутри которого одновременно роятся тысячи фреймов из сотен разных стримов.

### 🪵 «Разжёванный» пример: Как это выглядит на физическом уровне

Представь, что браузеру нужно одновременно скачать с твоего Node.js бэкенда три ресурса: `style.css`, `script.js` и `api/users` (JSON).

**Как бы это происходило в HTTP/1.1:**
Браузер открывает три TCP-канала. По первому течет текст CSS. По второму — JS. По третьему — JSON. Сервер тратит ресурсы на удержание трех сокетов. Если на одном из каналов тяжелый файл, этот канал забит до тех пор, пока файл не докачается.

**Как это происходит в HTTP/2 (Мультиплексирование):**
Открывается **один** TCP-канал. Браузер нарезает запросы на фреймы, помечает их ID и отправляет вперемешку. Сервер принимает их, обрабатывает и генерирует ответ. В сетевой провод фреймы ответа выстреливают в таком порядке:

```text
[Физический провод TCP-соединения]
<-- [Data: CSS (Stream 1)] -- [Data: JSON (Stream 5)] -- [Data: JS (Stream 3)] -- [Headers: JSON (Stream 5)] -- [Data: CSS (Stream 1)] <--
```


Сетевая карта сервера отправляет фреймы вперемешку. Браузер на другой стороне провода считывает заголовки фреймов, видит их Stream ID и моментально раскладывает их по трем разным «кучкам»:

  * Все фреймы с ID 1 склеиваются в файл style.css.

  * Все фреймы с ID 3 склеиваются в script.js.

  * Все фреймы с ID 5 превращаются в JSON для фронтенда.


> ℹ️ В чём профит? Маленький JSON (Stream 5) не ждет, пока скачается тяжелый CSS (Stream 1). Его фреймы просто проскакивают между фреймами стилей. Интерфейс пользователя загружается отзывчиво и плавно
