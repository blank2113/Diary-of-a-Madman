## **Алгоритмы балансировки: Round Robin (Циклический перебор)**

**Round Robin (Раунд Робин / Круговая система)** — это самый базовый, классический и наиболее широко используемый алгоритм балансировки нагрузки. Благодаря своей простоте он встроен по умолчанию практически в любой прокси-сервер или сетевой балансировщик (Nginx, HAProxy, Envoy, AWS ALB).

---

### Как работает алгоритм?

Принцип работы Round Robin — это простая **очередь по кругу**. Балансировщик хранит список доступных бэкенд-серверов и распределяет входящие запросы от клиентов строго по цепочке, один за другим. Когда список серверов заканчивается, балансировщик возвращается к первому серверу и начинает круг заново.

[Image of Round Robin load balancing algorithm distributing incoming sequential requests to a pool of backend servers in a circular order]

#### Живой пример:
У вас есть 3 инстанса Node.js приложения: `Server 1`, `Server 2` и `Server 3`.
* 1-й запрос от клиента отправляется на `Server 1`
* 2-й запрос от клиента отправляется на `Server 2`
* 3-й запрос от клиента отправляется на `Server 3`
* 4-й запрос от клиента возвращается на `Server 1`
* 5-й запрос — на `Server 2` и так далее.

> **Главная особенность:** Алгоритм является **Stateless** (не хранит состояние нагрузки). Он «вслепую» распределяет запросы, не проверяя, сколько процессорного времени или оперативной памяти сейчас свободно на каждом сервере.

---

### Модификация: Weighted Round Robin (С учетом весов)

В реальной жизни серверы в кластере часто имеют разную спецификацию: один работает на мощной виртуальной машине, а второй — на старом резервном железе. Чтобы слабый сервер не упал от перегрузки, используется модификация с **весами (Weights)**.

Каждому серверу вручную присваивается числовой коэффициент (вес). Чем выше вес, тем больше запросов сервер обработает за один цикл.

#### Пример распределения с весами:
* `Server 1` (Вес = 3)
* `Server 2` (Вес = 1)

За один цикл балансировщик отправит **3 запроса подряд** на `Server 1`, и только **1 запрос** на `Server 2`. Это позволяет распределять нагрузку пропорционально возможностям железа.

---

### Плюсы и минусы алгоритма

#### Преимущества:
* **Простота и скорость:** Балансировщику не нужно тратить ресурсы CPU на постоянный мониторинг состояния серверов, подсчет активных сокетов или анализ HTTP-сессий. Он просто сдвигает указатель на следующий элемент массива.
* **Детерминированность:** Поведение алгоритма легко предсказать и протестировать.
* **Идеален для Stateless-архитектуры:** Если ваши микросервисы не хранят сессии в памяти (а используют, например, JWT), Round Robin отлично распределит общий трафик.

#### Недостатки:
* **Проблема «тяжелых» запросов:** Если на `Server 1` по очереди прилетят три подряд тяжелых аналитических запроса, а на `Server 2` — три легких запроса авторизации, Round Robin все равно продолжит слать трафик поровну, что приведет к локальной перегрузке первого сервера.
* **Игнорирование текущего состояния:** Если один из серверов начнет тормозить из-за внутренней утечки памяти (Memory Leak) в Node.js, Round Robin не заметит этого и продолжит направлять туда пользователей (здесь на помощь приходит алгоритм *Least Connections*).

### Примеры конфигурации в прокси-серверах

#### 1. Настройка в Nginx
В Nginx алгоритм Round Robin является **стандартным поведением**. Если вы просто перечислите серверы в блоке `upstream`, включится именно он.

```nginx
http {
    upstream nestjs_cluster {
        # Сервер 1 примет в 3 раза больше запросов, чем Сервер 2
        server backend-node-1.local:3000 weight=3;
        server backend-node-2.local:3000 weight=1;
    }

    server {
        listen 80;
        location / {
            proxy_pass http://nestjs_cluster;
        }
    }
}
```

#### 2. Настройка в HAProxy
В HAProxy алгоритм включается директивой `balance roundrobin` в секции бэкенда:

```haproxy
backend nestjs_api_backend
    mode http
    balance roundrobin # Включаем циклический перебор
    
    server node-1 10.0.0.10:3000 check weight 2
    server node-2 10.0.0.11:3000 check weight 1
```

#### 3. Настройка в Envoy
В Envoy политика балансировки настраивается внутри параметров кластера через поле lb_policy:

```envoy
clusters:
- name: nestjs_cluster
  connect_timeout: 0.25s
  lb_policy: ROUND_ROBIN # Настройка циклического перебора в Envoy
  load_assignment:
    cluster_name: nestjs_cluster
    # ... описание эндпоинтов
```    

### Когда выбирать Round Robin?

* Когда все бэкенд-серверы имеют одинаковую аппаратную конфигурацию (CPU/RAM).

* Когда ваше приложение обрабатывает однородные, быстрые запросы (например, API отдает простые сущности из кэша Redis или раздает статический фронтенд).

* В качестве базовой настройки на старте проекта, пока вы не столкнулись со специфическими перекосами нагрузки.
