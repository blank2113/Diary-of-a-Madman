## **Алгоритмы балансировки: Least Connections (Наименьшее количество соединений)**

При распределении сетевого трафика между серверами приложений (например, инстансами NestJS) критически важно выбрать правильный алгоритм балансировки. Одним из самых эффективных динамических алгоритмов является **Least Connections (LeastConn)**.

В отличие от классического **Round Robin**, который «вслепую» шлет запросы по очереди на каждый сервер, Least Connections учитывает текущую нагрузку на бэкенды.

---

### Как работает алгоритм?

Принцип работы предельно прост: когда от клиента прилетает новый запрос, балансировщик (Nginx, HAProxy или Envoy) смотрит на свою внутреннюю таблицу активных сессий и направляет этот запрос на тот сервер, который **в данный конкретный момент обрабатывает меньше всего открытых соединений**.



#### Живой пример:
У вас есть 3 сервера приложений, запущенных через PM2 или Docker:
* `Server А` сейчас обрабатывает **45 активных запросов** (например, пользователи скачивают тяжелые отчеты).
* `Server Б` обрабатывает **10 активных запросов**.
* `Server В` обрабатывает **2 активных запроса**.

Если балансировщик настроен на *Round Robin*, он может отправить следующий запрос на `Server А`, рискуя перегрузить его CPU и заставить клиента ждать. 
Балансировщик с алгоритмом *Least Connections* моментально увидит, что `Server В` практически свободен, и отправит новый запрос именно ему.

---

### Модификация: Weighted Least Connections (С учетом весов)

Если ваши серверы имеют разную аппаратную мощность (например, один инстанс запущен на мощном сервере с 16 ядрами CPU, а второй — на слабенькой виртуальной машине с 2 ядрами), используется модификация алгоритма с учетом **весов серверов (Weights)**.

В этом случае балансировщик выбирает сервер на основе соотношения:
$$\text{Текущие соединения} \div \text{Вес сервера}$$

Побеждает сервер, у которого это значение оказывается наименьшим. То есть мощный сервер с большим весом будет получать приоритет даже в том случае, если на нем уже есть активные соединения.

---

### Когда Least Connections идеален?

1. **Асинхронные и разнородные запросы:** Когда время обработки запросов сильно отличается. Например, один эндпоинт (`GET /api/v1/health`) отрабатывает за 5 мс, а второй (`POST /api/v1/analytics/report`) генерирует PDF-файл в течение 10 секунд.
2. **Длинные сессии (Persistent Connections):** Отлично подходит для приложений с долгими HTTP-соединениями, стриминга данных или WebSocket-сессий.
3. **Защита от «каскадного падения» (Thundering Herd):** Если один из серверов упал, а затем перезапустился и вернулся в строй, Round Robin сразу же навалит на него стандартную порцию трафика. Least Connections будет плавно выравнивать нагрузку, отдавая новому (пока еще абсолютно свободному) серверу запросы до тех пор, пока он не догонит по числу соединений остальные ноды.

---

### Примеры конфигурации в прокси-серверах

#### 1. Настройка в HAProxy
В HAProxy этот алгоритм включается директивой `balance leastconn` в блоке бэкенда:

```haproxy
backend nestjs_api_cluster
    mode http
    balance leastconn # Включаем алгоритм наименьших соединений
    
    # Серверу node-2 дали больший вес, так как он мощнее
    server node-1 10.0.0.10:3000 check weight 1
    server node-2 10.0.0.11:3000 check weight 2
```

#### 2. Настройка в Nginx
В Nginx директива пишется как least_conn внутри блока upstream:

```ngnix
http {
    upstream nestjs_app {
        least_conn; # Включаем алгоритм
        
        server localhost:3000;
        server localhost:3001;
        server localhost:3002 backup; # Этот включится, только если остальные упадут
    }

    server {
        listen 80;
        location / {
            proxy_pass http://nestjs_app;
        }
    }
}
```

#### 3. Настройка в Envoy
В Envoy политика указывается в параметрах конкретного кластера через поле lb_policy:

```envoy
clusters:
- name: nestjs_cluster
  connect_timeout: 0.25s
  lb_policy: LEAST_REQUEST # В Envoy этот алгоритм называется Least Request
  load_assignment:
    cluster_name: nestjs_cluster
    # ... далее описание эндпоинтов
```    

### Сравнение с [Round Robin](./RoundRobin.md): Краткая шпаргалка

* Выбирайте [Round Robin](./RoundRobin.md), если все запросы к вашему серверу одинаково «легкие» (например, просто раздача статических HTML/CSS файлов) и все серверы имеют абсолютно одинаковую мощность.

* Выбирайте Least Connections, если в вашем API (на NestJS/Node.js) есть тяжелые вычислительные операции или запросы к базе данных, время выполнения которых непредсказуемо. Это гарантирует, что ни один инстанс приложения не захлебнется под кучей накопившихся задач.
