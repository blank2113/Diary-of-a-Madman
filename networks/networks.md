# Сети


**Компьютерные сети (Networks / Networking)** — это система, объединяющая два и более компьютера (или других устройства, вроде серверов, смартфонов и роутеров) с помощью кабелей или Wi-Fi для обмена данными и совместного использования ресурсов.

Из чего состоит любая сеть:

* Узлы (Nodes): Всё, что подключается к сети (ваш ноутбук, сервер с NestJS, база данных, умный чайник).

* Среда передачи: То, по чему летят данные (медный кабель «витая пара», оптоволокно или радиоволны Wi-Fi/LTE).

* Сетевое оборудование: Умные коробки, которые направляют трафик в нужное место (коммутаторы/свитчи, маршрутизаторы/роутеры).

* Протоколы: Набор правил и стандартов, благодаря которым устройства понимают друг друга (IP, TCP, UDP, HTTP).

> Суть сети в одной фразе: Это инфраструктура (дороги и знаки дорожного движения), которая позволяет вашему приложению доставить байты информации с одного компьютера на другой без потерь и путаницы.

<a id="L4L7"></a>
## **Модель OSI: Уровни L4 (Транспортный) и L7 (Прикладной)**

Для веб-разработчика и DevOps-инженера модель OSI — это не просто теоретическая абстракция из учебников, а практический инструмент для настройки серверов, проксирования и балансировки трафика. 

Хотя модель OSI состоит из 7 уровней, в контексте веб-разработки критически важно досконально понимать два из них: **L4 (Transport)** и **L7 (Application)**.

---

### Сетевая иерархия: В чем разница между L4 и L7?

Главное различие между этими уровнями — **глубина анализа данных**, которые проходят через сетевое устройство (например, балансировщик [Nginx](../nginx/nginx.md), [HAProxy](./HAProxy.md) или [Envoy](./Envoy.md)).



#### 1. Транспортный уровень (Layer 4 — L4)
На этом уровне живут протоколы **TCP** и **UDP**. 

* **Что видит балансировщик на L4:** Он видит только IP-адрес отправителя/получателя и порты. Он **не заглядывает** внутрь передаваемых данных. Для него весь трафик — это просто поток байт.

* **Как работает балансировка на L4:** Балансировщик принимает TCP-соединение от клиента и мгновенно перенаправляет его на один из целевых серверов (upstream) по простому алгоритму (например, [Round Robin](./RoundRobin.md) или [Least Connections](./LeastConnection.md)), основываясь только на IP и порте.

* **Плюсы L4:** * Невероятно высокая скорость и производительность.
  * Тратится минимум CPU и памяти, так как серверу не нужно парсить, расшифровывать (SSL/TLS) или читать пакеты.

* **Минусы L4:**
  * Полная «слепота». Нельзя принять решение о маршрутизации на основе URL, кук или заголовков (потому что балансировщик их просто не видит).

#### 2. Прикладной уровень (Layer 7 — L7)
На этом уровне живут протоколы приложений: **HTTP**, **HTTPS**, **FTP**, **WebSocket**, **SMTP**.

* **Что видит балансировщик на L7:** Он видит абсолютно всё. Ему доступен весь HTTP-запрос: заголовки (Headers), куки (Cookies), URI (путь вроде `/api/v1/users`), метод (`GET`/`POST`) и тело запроса (JSON, форм-дата).

* **Как работает балансировка на L7:** Чтобы принять решение, куда отправить запрос, L7-прокси должен сначала полностью установить TCP-соединение с клиентом, принять все пакеты, **расшифровать SSL/TLS**, распарсить HTTP-текст и только после этого перенаправить запрос на нужный инстанс Node.js/NestJS.

* **Плюсы L7:**
  * Умная маршрутизация. Можно отправить запросы `/api/auth/*` на один микросервис, а `/static/*` — на другой.
  * Возможность аутентификации на уровне прокси, склеивания сессий по Cookies (Session Stickiness), ограничение частоты запросов (Rate Limiting) по ID пользователя.

* **Минусы L7:**
  * Намного медленнее, чем L4.
  * Требует значительных ресурсов CPU для парсинга трафика и терминации SSL (дешифрования).

---

### Сравнительная таблица для проксирования

| Критерий | L4 Проксирование (TCP/UDP) | L7 Проксирование (HTTP) |
| :--- | :--- | :--- |
| **Протоколы** | TCP, UDP | HTTP, HTTPS, WebSocket, gRPC |
| **Что анализируется** | IP-адреса и порты | URL, Заголовки, Куки, Тело запроса |
| **Терминация SSL/TLS** | Нет (трафик проходит зашифрованным) | Да (прокси сам расшифровывает трафик) |
| **Нагрузка на CPU** | Мизерная | Высокая |
| **Гибкость настроек** | Низкая (просто пересылка пакетов) | Максимальная (умный роутинг) |
| **Примеры применения** | Балансировка баз данных (PostgreSQL, Redis), gRPC (стримы), raw TCP-сокеты. | Микросервисная архитектура, API Gateway, веб-сайты. |

---

### Как это выглядит в конфигурации Nginx

В Nginx разделение на L4 и L7 выглядит очень наглядно на уровне конфигурационных блоков.

#### Пример L4 балансировки (Блок `stream`)
Используется, например, для распределения нагрузки между несколькими нодами базы данных PostgreSQL:

```nginx
# L4 работа в Nginx настраивается вне блока http
stream {
    upstream postgres_servers {
        server pg-node1.local:5432;
        server pg-node2.local:5432;
    }

    server {
        listen 5432; # Слушаем порт базы данных
        proxy_pass postgres_servers; # Просто перекидываем TCP-пакеты
    }
}
```

## **2. Структура IP-адресов**

**IP-адрес (Internet Protocol Address)** — это уникальный числовой идентификатор устройства (компьютера, сервера, роутера, смартфона), подключенного к компьютерной сети. Без IP-адреса устройство не может отправлять или получать сетевые пакеты, так как маршрутизаторы просто не будут знать, куда их доставлять.

В современной практике сожительствуют две версии протокола IP: **IPv4** и **IPv6**.

---

### IPv4 (Internet Protocol version 4)

Это классический и до сих пор самый распространенный стандарт адресации, разработанный еще в начале 1980-х годов.

#### Как устроен IPv4-адрес под капотом:
* **Длина адреса:** Ровно **32 бита** (или 4 байта).
* **Формат записи:** Для удобства людей эти 32 бита разбивают на 4 группы по 8 бит (каждая группа называется **октетом**) и записывают в десятичном виде через точку.
* **Диапазон:** Так как 8 бит могут принимать значения от `00000000` до `11111111`, в десятичной системе каждый октет может быть числом **от 0 до 255**.



> **Пример:** `192.168.1.50`
> В двоичном виде для компьютера этот адрес выглядит так:
> `11000000 . 10101000 . 00000001 . 00110010`

#### Анатомия адреса: Сеть и Хост
Любой IP-адрес делится на две части: одна часть указывает на **номер сети**, а вторая — на **номер конкретного устройства (хоста)** в этой сети. 

Чтобы компьютер понимал, где заканчивается адрес сети и начинается адрес хоста, используется **Маска подсети (Subnet Mask)**.

* Если маска выглядит как `255.255.255.0`, это значит, что первые 3 октета (`192.168.1.`) — это адрес вашей локальной сети, а последний октет (`50`) — уникальный номер вашего компьютера.
* В современной разработке и DevOps вместо длинной маски используют компактную **CIDR-нотацию** (количество бит, выделенных под сеть). Запись `192.168.1.50/24` означает, что первые 24 бита (3 октета по 8 бит) отданы под адрес сети.

#### Главная проблема IPv4: Исчерпание адресов
Максимальное количество уникальных адресов в IPv4 ограничено математически: 
$$2^{32} \approx 4.3 \text{ миллиарда адресов}$$

Поскольку сейчас у каждого человека по несколько гаджетов, а в продакшене крутятся миллионы виртуальных машин и Docker-контейнеров, свободные IPv4-адреса на планете официально закончились. Мир временно спасается технологией **NAT** (когда весь ваш офис или дом выходит в интернет через один общий внешний IP роутера), но глобальное решение — это переход на IPv6.

---

### IPv6 (Internet Protocol version 6)

IPv6 — это новая версия сетевого протокола, созданная для того, чтобы полностью решить проблему дефицита адресов и убрать костыли в виде NAT.

#### Как устроен IPv6-адрес под капотом:
* **Длина адреса:** **128 бит** (в 4 раза длиннее, чем IPv4).
* **Формат записи:** Записывать такое количество цифр в десятичном виде было бы нереально, поэтому IPv6 пишут в **шестнадцатеричной системе** (цифры от 0 до 9 и буквы от A до F). Адрес разделяется двоеточиями на 8 групп по 4 символа (каждая группа называется *хекстетом* и весит 16 бит).



> **Пример:** `2001:0db8:85a3:0000:0000:8a2e:0370:7334`
> Поскольку адреса огромные, правила разрешают отбрасывать ведущие нули и заменять идущие подряд группы нулевых хекстетов двойным двоеточием `::`. Сокращенный адрес выглядит так: `2001:db8:85a3::8a2e:370:7334`.

#### Емкость сети IPv6:
Количество уникальных адресов в IPv6 составляет:
$$2^{128} \approx 3.4 \times 10^{38}$$

Это астрономическое число (более 340 андециллионов). Этого запаса хватит, чтобы присвоить уникальный IP-адрес каждому атому на поверхности Земли, и еще останется. При использовании IPv6 концепция NAT больше не нужна — каждое устройство в мире получает свой честный, уникальный «белый» адрес.

---

### Белые (Публичные) и Серые (Приватные) IP-адреса

Для безопасности и экономии все IP-адреса (в основном это касается IPv4) разделили на два типа:

1. **Публичные ("Белые") адреса:** Используются в глобальном интернете. Маршрутизаторы по всему миру знают, как доставить туда пакет. Любой сервер в облаке (где крутится ваш Nginx или NestJS) обязан иметь белый IP, иначе клиенты из дома не смогут до него достучаться.
2. **Приватные ("Серые") адреса:** Используются только внутри локальных сетей (внутри вашей квартиры, офиса или закрытого дата-центра). Эти адреса не маршрутизируются в интернете.

Для серых сетей зарезервированы строгие диапазоны, которые вы точно постоянно видите в конфигах:
* `192.168.0.0 — 192.168.255.255` (домашние роутеры)
* `172.16.0.0 — 172.31.255.255` (часто используется в Docker-сетях и AWS)
* `10.0.0.0 — 10.255.255.255` (крупные корпоративные сети и кластеры)

> **Специальный адрес (Loopback):** Адрес `127.0.0.1` (в IPv6 записывается как `::1`) — это локальная петля (localhost). Он указывает на саму вашу машину. Когда вы тестируете Node.js приложение на своем ноутбуке, вы обращаетесь именно к этому IP.

---

### Сводная шпаргалка: IPv4 vs IPv6

| Критерий | IPv4 | IPv6 |
| :--- | :--- | :--- |
| **Размер адреса** | 32 бита | 128 бит |
| **Тип записи** | Десятичный (`192.168.1.1`) | Шестнадцатеричный (`2001:db8::1`) |
| **Разделитель** | Точка (`.`) | Двоеточие (`:`) |
| **Количество адресов** | ~4.3 миллиарда | Множество ($3.4 \times 10^{38}$) |
| **Встроенная безопасность** | Опционально (IPsec) | Обязательно (IPsec встроен в стандарт) |
| **Использование NAT** | Необходимо повсеместно | Не требуется |

<a id="PortsAndSocets"></a>
## **3. Порты и Сокеты**

Если IP-адрес позволяет сетевому пакету найти нужный компьютер в глобальной или локальной сети, то порты и сокеты определяют, какая именно программа на этом компьютере должна получить данные.

---

### Порты (Ports)

**Порт** — это числовой идентификатор внутри операционной системы, который выделяется конкретному приложению для обмена данными по сети. 

Представьте, что IP-адрес — это адрес большого многоквартирного дома. Вы не можете просто отправить письмо «в дом №10», вам нужно указать номер квартиры. **Порт — это и есть номер квартиры**, закрепленный за конкретным процессом (например, сервером NestJS или базой данных).

#### Ограничения и классификация портов:
Порт представляет собой 16-битное число, поэтому его диапазон строго ограничен: **от 0 до 65535**. По общепринятым стандартам (IANA) весь этот диапазон разделен на три группы:

1. **Well-known ports (Системные / Общеизвестные): от 0 до 1023**
   Эти порты зарезервированы за важнейшими системными службами и стандартными сетевыми протоколами. Чтобы запустить приложение на этих портах в Unix-подобных системах (Linux, macOS), требуются права суперпользователя (`root` / `sudo`).
   * `22` — SSH (безопасный удаленный доступ)
   * `53` — DNS (служба доменных имен)
   * `80` — HTTP (незащищенный веб-трафик)
   * `443` — HTTPS (защищенный веб-трафик)

2. **Registered ports (Зарегистрированные): от 1024 до 49151**
   Эти порты выделяются под популярные сторонние приложения, базы данных и фреймворки. Их может использовать любой рядовой процесс пользователя.
   * `3000` — Стандартный порт для локального запуска Node.js / React / NestJS приложений
   * `5432` — СУБД PostgreSQL
   * `6379` — СУБД Redis
   * `8080` — Альтернативный порт для веб-серверов и прокси (Nginx, Apache)

3. **Dynamic / Private ports (Динамические / Приватные): от 49152 до 65535**
   Эти порты операционная система выделяет временно и динамически для клиентских приложений (например, вашего браузера), когда они инициируют подключение к удаленному серверу.

---

### Сетевые сокеты (Sockets)

**Сокет (Socket)** — это не физический объект и не протокол, а программная абстракция, конечная точка (Endpoint) двустороннего канала связи между двумя программами в сети.

Чтобы операционная система могла однозначно идентифицировать конкретный сетевой канал, сокет создается на основе строгого математического кортежа:
$$\text{Socket} = \text{IP-адрес} + \text{Протокол (TCP/UDP)} + \text{Номер порта}$$

Когда клиент (например, ваш браузер) подключается к серверу (например, к API на NestJS), в сети образуется **пара сокетов (Socket Pair)**, которая связывает их воедино.



#### Как это работает на живом примере:
У вас есть сервер с IP `95.213.255.1`, на котором запущен NestJS на порту `3000`.
1. Сервер открывает **слушающий сокет (Listening Socket)**: `95.213.255.1:3000:TCP`. Он находится в режиме ожидания.
2. Вы со своего ноутбука (IP `172.20.10.2`) открываете браузер и переходите на этот сайт. 
3. Операционная система вашего ноутбука выделяет браузеру случайный свободный порт из динамического диапазона (например, `51423`) и создает **клиентский сокет**: `172.20.10.2:51423:TCP`.
4. В момент рукопожатия (Handshake) между ними создается уникальная сессия связи, состоящая из пары сокетов:
   `172.20.10.2:51423` <───> `95.213.255.1:3000`

---

### Сокеты под капотом Node.js

В Node.js работа с сетевыми подключениями и сокетами реализована на самом низком уровне в модуле `net` (для TCP) и `dgram` (для UDP). Когда вы пишете код на NestJS или Express, фреймворки лишь прячут от вас эту низкоуровневую логику.

Объект `Socket` в Node.js является **дуплексным потоком (Duplex Stream)** — в него можно как записывать данные (`socket.write()`), так и читать их оттуда через события (`socket.on('data')`).

#### Пример: Получение данных сокета в HTTP-запросе Node.js
Даже в стандартном высокоуровневом HTTP-сервере у вас всегда есть прямой доступ к сетевому сокету через свойство `req.socket`. Это бывает критически важно для логирования, безопасности или геолокации.

```typescript
import * as http from 'http';

const server = http.createServer((req: http.IncomingMessage, res: http.ServerResponse) => {
  // Достаем данные сокета клиента напрямую из сетевого уровня операционной системы
  const clientIp = req.socket.remoteAddress; // IP-адрес клиента
  const clientPort = req.socket.remotePort;   // Временный порт, который выделила ОС клиента
  const serverPort = req.socket.localPort;    // Порт самого сервера, куда прилетел запрос (3000)

  console.log(`Новое TCP соединение от сокета: ${clientIp}:${clientPort}`);

  res.writeHead(200, { 'Content-Type': 'text/plain' });
  res.end(`Ваш сетевой адрес на уровне сокета: ${clientIp}:${clientPort}`);
});

server.listen(3000);
```
