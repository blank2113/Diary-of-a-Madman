## **HAProxy: Высокопроизводительный балансировщик L4 и L7**

**HAProxy (High Availability Proxy)** — это популярное с открытым исходным кодом программное обеспечение, предназначенное для балансировки нагрузки (Load Balancing) и проксирования TCP (L4) и HTTP (L7) приложений. 

Его ценят за невероятную скорость, стабильность и эффективное использование ресурсов CPU и оперативной памяти. В отличие от Nginx, который создавался как веб-сервер и умеет отдавать статические файлы с диска, **HAProxy спроектирован исключительно как прокси и балансировщик**.

---

### Основные концепции архитектуры HAProxy

Конфигурация HAProxy строится вокруг четырех главных блоков:

1. **`global`**: Глобальные настройки процесса (пользователь, под которым запускается демон, логирование, лимиты памяти).
2. **`defaults`**: Настройки по умолчанию для всех остальных секций (таймауты, режимы работы), чтобы не дублировать код.
3. **`frontend`**: Описывает, как HAProxy принимает входящие соединения от клиентов (какой IP, порт и протокол слушать, какие правила ACL применять).
4. **`backend`**: Список серверов (upstream/target), на которые HAProxy будет перенаправлять очищенный и отбалансированный трафик, а также алгоритмы балансировки и правила проверки здоровья (Health Checks).

---

### Практический пример 1: Балансировка на уровне L4 (TCP)

В режиме L4 (`mode tcp`) HAProxy работает как «глухой» переключатель пакетов. Он не знает, что находится внутри сессии, и просто пересылает входящие байты на свободный сервер. 

Этот режим идеально подходит для баз данных (например, кластера PostgreSQL или Redis).



```haproxy
global
    log /dev/log local0
    maxconn 4096

defaults
    log     global
    mode    tcp           # Указываем режим работы по умолчанию
    timeout connect 5s    # Время ожидания соединения с бэкендом
    timeout client  50s   # Время ожидания активности от клиента
    timeout server  50s   # Время ожидания ответа от бэкенда

# Настройка приема трафика
frontend postgres_in
    bind *:5432           # Слушаем входящие соединения на порту БД
    default_backend postgres_pool

# Настройка распределения трафика
backend postgres_pool
    balance roundrobin    # Алгоритм балансировки: по очереди каждому
    
    # Интенсивный TCP-чекинг: проверяем, отвечает ли порт сервера
    option tcp-check
    
    # Список наших серверов баз данных
    server pg-node-1 192.168.1.11:5432 check
    server pg-node-2 192.168.1.12:5432 check
```

### **Практический пример 2: Умная балансировка на уровне L7 (HTTP)**
В режиме L7 (mode http) HAProxy полностью парсит HTTP-запросы. Здесь мы можем использовать ACL (Access Control Lists) для реализации сложного роутинга: например, разделять API-трафик и статику или защищаться от DDOS-атак.

```text
global
    log /dev/log local0
    chroot /var/lib/haproxy
    user haproxy
    group haproxy

defaults
    log     global
    mode    http          # Включаем режим парсинга HTTP
    timeout connect 5000ms
    timeout client  50000ms
    timeout server  50000ms

frontend http_in
    bind *:80             # Слушаем обычный веб-трафик
    
    # Определение правил ACL (Access Control Lists)
    # Проверяем, начинается ли URL-путь с /api
    acl is_api path_beg /api
    # Проверяем, начинается ли URL-путь с /static или /images
    acl is_static path_beg /static /images

    # Умная маршрутизация на основе правил ACL
    use_backend nestjs_api_backend if is_api
    use_backend static_backend     if is_static
    
    # Бэкенд по умолчанию (если ни одно правило не подошло)
    default_backend frontend_apps_backend

# Бэкенд для NestJS приложений
backend nestjs_api_backend
    balance leastconn     # Алгоритм: отправлять запрос туда, где сейчас меньше всего активных соединений
    option httpchk GET /api/health # Умная проверка здоровья: дергаем эндпоинт приложения
    
    # Серверы с Node.js/NestJS
    server nestjs-node-1 10.0.0.10:3000 check inter 2000 rise 2 fall 3
    server nestjs-node-2 10.0.0.11:3000 check inter 2000 rise 2 fall 3

# Бэкенд для раздачи статического контента (например, Nginx-ноды)
backend static_backend
    balance roundrobin
    server static-server-1 10.0.0.20:8080 check

# Бэкенд для SPA-фронтенда
backend frontend_apps_backend
    balance roundrobin
    cookie SERVERID insert indirect nocache # Привязка сессии (Session Stickiness) через куки
    server web-front-1 10.0.0.5:80 check cookie s1
    server web-front-2 10.0.0.6:80 check cookie s2
```    


### Пояснения к важным параметрам из примеров:

* **`inter 2000`**: ИнInterval (интервал). Делать проверку здоровья (Health Check) бэкенд-сервера каждые 2000 миллисекунд (2 секунды).

* **`fall 3`**: Количество падений. Если сервер ответил ошибкой или не ответил 3 раза подряд, HAProxy помечает его как *DEAD* (неактивный) и убирает из балансировки, чтобы реальные пользователи не получали ошибок.

* **`rise 2`**: Количество подъемов. Когда ранее «упавший» сервер снова оживает, ему нужно успешно пройти проверку здоровья 2 раза подряд, прежде чем HAProxy признает его стабильным и начнет слать на него реальный трафик.

* **`cookie SERVERID insert`**: Механизм **Session Stickiness** (привязка сессии). HAProxy внедряет собственную куку в HTTP-ответ пользователю. Когда этот же пользователь делает следующий запрос, HAProxy считывает куку (например, `s1`) и отправляет его строго на тот же сервер (`web-front-1`). Это критично, если ваше Node.js/NestJS приложение хранит сессии локально в памяти инстанса, а не в общем Redis.

### Ключевые отличия: Когда выбирать HAProxy, а когда Nginx?

| Критерий сравнения | HAProxy | Nginx |
| :--- | :--- | :--- |
| **Основное назначение** | Исключительно балансировщик нагрузки и прокси-сервер. | Универсальный веб-сервер, обратный прокси и балансировщик. |
| **Раздача статики (HTML, CSS, JS)** | **Не умеет** читать файлы с диска. Нельзя указать `root` или `try_files`. | **Идеально** отдает статику с диска на огромной скорости, кэширует файлы. |
| **Производительность под нагрузкой** | Показывает более высокую стабильность и предсказуемое потребление RAM при сотнях тысяч одновременных TCP/HTTP соединений. | Отличная производительность, но тратит чуть больше ресурсов на логику обработки соединений. |
| **Встроенный мониторинг** | Из коробки предоставляет мощную графическую панель **HAProxy Stats** с метриками задержек, сессий и аптайма бэкендов. | Подробный графический дашборд доступен только в платной версии (Nginx Plus). В бесплатной — только текстовый stub_status. |
| **Гибкость балансировки (L7)** | Обладает невероятно мощным и гибким движком ACL для разбора HTTP-пакетов на лету. | Предлагает отличный, интуитивно понятный роутинг через блоки `location`. |

#### Резюме по выбору:
* Выбирайте **HAProxy**, если вам нужен «чистокровный», сверхбыстрый балансировщик перед группой тяжелых серверов приложений (микросервисов), кластером баз данных (PostgreSQL, Redis) или gRPC-потоков, а также если вам важна детальная встроенная аналитика трафика.

* Выбирайте **Nginx**, если вам комбайн «все в одном»: нужно не только балансировать запросы на NestJS, но и тут же, силами самого прокси, отдавать собранный фронтенд (React/Vue/Angular) в виде статических файлов.
