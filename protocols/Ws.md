# 🔌 **WebSockets (WS / WSS): Полнодуплексный интерактив в Web**

Классический протокол HTTP отлично подходит для загрузки статических страниц, документов или стандартных REST-запросов, но он совершенно не приспособлен для построения интерактивных систем реального времени (Real-Time Apps). 

Поскольку HTTP работает по жесткой схеме «клиент запросил — сервер ответил», сервер не может самостоятельно инициировать передачу данных клиенту. **WebSockets (WS)** решает эту проблему, предоставляя постоянное, двунаправленное и легковесное соединение.

---

## 1. Как работает WebSocket: Процесс Handshake

Протокол WebSocket начинается как обычный HTTP-запрос, но в процессе общения клиент и сервер договариваются о «смене вывески». Этот процесс называется **Handshake (Рукопожатие)**.



### Анатомия рукопожатия:

1. **Запрос клиента (HTTP Upgrade):**
   Браузер отправляет стандартный GET-запрос на специальный URL (например, `ws://api.mysite.com/socket`), добавляя заголовки, требующие переключения протокола:
   ```http
   GET /socket HTTP/1.1
   Host: api.mysite.com
   Upgrade: websocket
   Connection: Upgrade
   Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
   Sec-WebSocket-Version: 13
   ```

2. **Ответ сервера (101 Switching Protocols):**
  
    Если бэкенд (например, ваш сервер на NestJS) поддерживает WebSockets, он соглашается и возвращает статус 101   

    ```http
    HTTP/1.1 101 Switching Protocols
    Upgrade: websocket
    Connection: Upgrade
    Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
    ```

3. **Установление постоянного канала:**
    
    После этого HTTP-сессия полностью закрывается. Тот же самый TCP-сокет переходит в режим WebSocket. Теперь обе стороны могут слать бинарные или текстовые пакеты (кадры / frames) в любой момент времени без накладных расходов на HTTP-заheaders.

## 2. Безопасность: WS против WSS
По аналогии с HTTP и HTTPS, у протокола веб-сокетов есть две версии:

  * ***ws:// (WebSocket)***: Данные передаются в открытом текстовом/бинарном виде поверх обычного TCP. Любой злоумышленник в локальной сети (например, через открытый Wi-Fi в кафе) может перехватить переписку из чата или приватные токены.

  * ***wss:// (WebSocket Secure)***: Трафик оборачивается в защищенный слой SSL/TLS.

>Внимание для Production: В реальных приложениях всегда используйте только WSS. Современные браузеры заблокируют попытку открыть небезопасный ws:// сокет, если сам ваш сайт работает по HTTPS (политика Mixed Content).   


### 3. Сравнение: WebSockets против Long-Polling и SSE

До появления WebSockets инженерам приходилось изощряться, чтобы симулировать реалтайм. Вот три главные технологии, которые борются за эту задачу:

| Критерий | HTTP Long-Polling | Server-Sent Events (SSE) | WebSockets (WS) |
| :--- | :--- | :--- | :--- |
| **Направление связи** | Однонаправленное (Клиент ➔ Сервер) | Однонаправленное (Сервер ➔ Клиент) | **Дуплекс (Двунаправленное)** |
| **Протокол под капотом** | Стандартный HTTP | Стандартный HTTP | Свой протокол (после Handshake) |
| **Накладные расходы** | **Огромные.** На каждый чих открывается новый HTTP-запрос с полными заголовками. | **Минимальные.** Одно открытое HTTP-соединение. | **Самые низкие.** Пакеты данных весят всего несколько байт сверху. |
| **Формат данных** | Любой (JSON, текст) | Только текст (Stream текстовых событий) | Текст (строки, JSON) или бинарные данные (Blob, ArrayBuffer) |
| **Use Case** | Устаревший подход, костыль для старых браузеров. | Ленты уведомлений, биржевые котировки, подписка на логи (где клиенту не нужно слать частые ответы). | Чаты, многопользовательские онлайн-игры, совместное редактирование документов (Google Docs). |

## 4. Архитектурная проблема: Масштабирование WebSockets

Если ваше приложение на Node.js/NestJS работает на одном сервере, WebSockets работают идеально. Но что произойдет, если проект вырастет, и вы запустите 3 инстанса бэкенда за балансировщиком Nginx?

  * ***Проблема***: Пользователь Вася подключился сокетом к Instance 1, а пользователь Петя — к Instance 2. Если Вася отправит сообщение Пете, Instance 1 ничего не знает про Петю, потому что его сетевой сокет удерживается процессом Instance 2. Сообщение пропадет.

  * ***Решение (Redis Pub/Sub)***: Для масштабирования веб-сокетов инстансы бэкенда объединяют общим слоем обмена сообщениями — Redis Adapter. Когда Вася шлет сообщение, Instance 1 публикует его в общую шину Redis. Все остальные инстансы ловят это событие, и Instance 2 успешно доставляет его Пете через его сокет.

## 5. Реализация на Node.js (TypeScript / NestJS)

В экосистеме Node.js для работы с сокетами чаще всего используется библиотека Socket.io (она предоставляет удобные комнаты, автоматические переподключения и фолбэк на лонг-поллинг) или чистый, легковесный пакет ws.

**Пример чистого WebSocket-сервера (ws):**

```javascript
import { WebSocketServer, WebSocket } from 'ws';

// Запускаем сервер сокетов на порту 8080
const wss = new WebSocketServer({ port: 8080 });

wss.on('connection', (ws: WebSocket) => {
  console.log('Новый клиент подключился!');

  // Слушаем сообщения от конкретного клиента
  ws.on('message', (message: string) => {
    console.log(`Получено: ${message}`);
    
    // Эхо-ответ обратно клиенту
    ws.send(`Сервер получил ваш пакет: ${message}`);
  });

  // Отправляем приветственное сообщение при подключении
  ws.send('Добро пожаловать в реалтайм сеть!');
});
```

## 6. Настройка [Nginx](../nginx/nginx.md) для проксирования WebSockets
Поскольку WebSockets ломают стандартный цикл HTTP, Nginx нужно явно обучить пробрасывать заголовки апгрейда протокола, иначе он просто оборвет соединение через пару секунд.

```nginx
upstream nestjs_websocket_nodes {
    server 127.0.0.1:8080;
}

server {
    listen 443 ssl;
    server_name wss.mysite.com;

    location /socket {
        proxy_pass http://nestjs_websocket_nodes;

        # Переключаем прокси на HTTP/1.1 (критично для сокетов)
        proxy_http_version 1.1;

        # Магия проброса WebSocket-заголовков
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        # Пробрасываем реальные IP клиентов
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;

        # Важно: увеличиваем таймаут чтения. Если клиент и сервер молчат 
        # (нет пингов), Nginx закроет сокет по дефолту через 60 секунд.
        # Ставим 24 часа, управление пингами отдаем на откуп коду приложения.
        proxy_read_timeout 86400s;
        proxy_send_timeout 86400s;
    }
}
```
